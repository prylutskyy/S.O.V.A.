# Архітектура та структура проєкту Threat Shield

Цей документ описує організацію файлів у проєкті та правила, яких слід дотримуватись при розробці та додаванні нових модулів. Ми використовуємо фреймворк **WXT** для розробки розширень, що накладає певні вимоги до структури.

## Огляд директорій

### 1. `entrypoints/`
**ПРИЗНАЧЕННЯ:** Тут знаходяться точки входу розширення. Фреймворк WXT автоматично сканує цю папку для генерації `manifest.json`.
* **Правило:** Жодної бізнес-логіки тут! Тільки ініціалізація та налаштування слухачів (listeners). Усі важкі функції слід імпортувати з папки `src/`.
* **Вміст:** `background.ts`, `content.ts`, `popup/`

### 2. `src/`
**ПРИЗНАЧЕННЯ:** Основна папка для зберігання всього сирцевого коду розширення, розбитого за функціональним призначенням (Business Logic).

* **`src/core/`**: Ядро системи. Менеджери доступу, збереження даних (Local/Session Storage), криптографія, налаштування та базові сервіси.
  * *Приклади:* `personal-vault.ts`, `crypto-service.ts`, `user-whitelist.ts`
* **`src/heuristics/`**: Логіка детектування загроз (AI, евристика, регулярні вирази, аналіз DOM).
  * *Приклади:* `vault-scanner.ts`, `lure-detector.ts`, `intent-classifier.ts`
* **`src/ui/`**: UI компоненти, які безпосередньо інжектуються на сторінки (через Content Scripts). Управління DOM-елементами, Shadow DOM, модалками тощо.
  * *Приклади:* `unified-modal.ts`, `shadow-host.ts`, `intent-highlighter.ts`
* **`src/xai/`**: Explainable AI. Рушій для пояснення прийнятих рішень щодо загроз.
  * *Приклади:* `xai-engine.ts`
* **`src/types/`**: Усі TypeScript інтерфейси та типи, які використовуються у проєкті.
  * *Приклади:* `index.ts`, `vault.ts`, `xai.ts`

### 3. `tests/`
**ПРИЗНАЧЕННЯ:** Тести проєкту. Розділені за типом тестування для зручності CI/CD.
* **`tests/unit/`**: Юніт-тести, які тестують окремі функції чи класи ізольовано. Дзеркально повторює структуру папки `src/`.
  * *Приклади:* `tests/unit/core/crypto-service.test.ts`
* **`tests/integration/`**: Інтеграційні тести, які перевіряють взаємодію кількох модулів разом.
* **`tests/e2e/`** *(у майбутньому)*: End-to-End тести, які запускають реальний браузер.

## Правила створення нових файлів

1. **Де створювати новий файл?**
   * **Детектор загроз?** -> Створюйте в `src/heuristics/`.
   * **Глобальний менеджер (дані/стан)?** -> Створюйте в `src/core/`.
   * **Нова модалка або банер?** -> Створюйте в `src/ui/`.
   * **Тест для існуючого файлу?** -> Створюйте в `tests/unit/[назва-папки]/`.

2. **Іменування файлів:**
   * Використовуйте `kebab-case` для назв файлів (наприклад, `vault-scanner.ts`).
   * Не додавайте префіксів типу `class` чи `interface`.

3. **Розміщення бізнес-логіки:**
   * Уникайте написання логіки обробки даних безпосередньо в `content.ts` чи `background.ts`. 
   * Створіть клас або функцію у відповідній папці всередині `src/`, а в `entrypoints/` просто викличте її.

4. **Тестування (TDD):**
   * Перед створенням або зміною критичного модуля (як-то криптографія чи робота з даними), спочатку створіть файл тесту у відповідній директорії `tests/unit/`.
   * Тести мають запускатися локально командою `npx vitest run`.
