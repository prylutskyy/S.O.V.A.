# Архітектурний Аналіз та План Покращення (Threat Shield)

Цей документ містить аналіз поточних архітектурних рішень розширення, виявлені проблеми, які можуть призводити до хибних спрацьовувань (false positives) або вразливостей, а також пропозиції щодо переходу до розробки виключно за принципом Test-Driven Development (TDD).

---

## 1. Аналіз: Розпізнавання Наміру (Intent Classifier)

**Поточна реалізація:** 
Клас `IntentClassifier` використовує жорсткі регулярні вирази (RegEx) для пошуку ключових слів, об'єднує їх у "кластери" (наприклад, `delivery_action`, `urgency_pressure`) і нараховує бали (`weight`). Якщо сума балів перевищує певний поріг і знайдено потрібну комбінацію кластерів, фіксується фішинговий намір.

🟢 **Що добре:**
* Дуже швидке виконання, нульова затримка для користувача.
* Працює 100% локально (без відправки тексту на сервери), що гарантує конфіденційність.

🔴 **Що погано (Причини False Positives):**
* **Відсутність контексту:** Регулярні вирази не розуміють семантики. Повідомлення від родича *"Скинь номер картки для оплати"* може дати такий самий бал, як і від шахрая.
* **Обфускація шахраїв:** Шахраї постійно змінюють написання (наприклад, `о п л а т а`, `0лx`, `v1ber`), що вимагає постійного ручного розширення RegEx-словників.
* **Неможливість юніт-тестування масштабу:** Зміна однієї ваги може "полагодити" один кейс, але зламати 10 інших, і без автоматизованої бази тестових повідомлень це неможливо виявити.

💡 **Архітектурні покращення:**
1. **Інтеграція Machine Learning у браузер:** Перевести архітектуру з RegEx на легкомодельний NLP (Natural Language Processing). Наприклад, використання Chrome Built-in AI (Prompt API) або легкої ONNX-моделі (через `transformers.js`), яка завантажується локально. Це дасть розуміння контексту і знизить False Positives на 90%.
2. **Fuzzy Matching замість RegEx:** Використовувати алгоритми відстані Левенштейна або N-gram для знаходження обфускованих слів шахраїв.

## 2. Аналіз: Інтелектуальне Зшиття Сесій (Context Manager)

**Поточна реалізація:** 
Коли `IntentClassifier` у контент-скрипті (наприклад, на OLX) виявляє загрозу, він відправляє повідомлення у `background.ts`. Той, у свою чергу, викликає `ContextManager.setTaintedContext()`, який записує "отруєний" стан (Tainted Context) у `chrome.storage.session` на 15 хвилин. Будь-яка інша відкрита вкладка тепер знає про цей стан і працює в режимі підвищеної готовності.

🟢 **Що добре:**
* Відмінна модель загроз (Threat Model): атаки соціальної інженерії дійсно розподілені у часі та між різними вкладками (з чату -> у нову вкладку з фішингом).
* Використання RAM (`session storage`) гарантує, що стан скидається після перезапуску.

🔴 **Що погано (Причини False Positives):**
* **Глобальне зараження:** Стан записується глобально. Якщо користувач паралельно відкриє легітимний сайт банку чи оплати, поки триває 15-хвилинне "зараження" з OLX, цей легітимний сайт може бути заблокований, що викличе величезне роздратування користувача.
* **Втрата Tab Lineage:** Ми не знаємо, *яка саме* вкладка була відкрита зловмисником.

💡 **Архітектурні покращення:**
1. **Відстеження генеалогії вкладок (Tab Lineage):** `ContextManager` має використовувати `chrome.tabs.onCreated` та `openerTabId`, щоб зв'язувати контекст лише з тією вкладкою, з якої почалась атака (та з її дочірніми вкладками).
2. **Динамічний TTL:** Таймер зараження має зменшуватись або скидатись, якщо користувач успішно перейшов на довірений сайт (наприклад, офіційний сайт ПриватБанку).

## 3. Перехід на TDD та Покращення безпеки коду

Наразі архітектура сильно "зв'язана" (tightly coupled) з API браузера (`chrome.*` або `window.*`). Це робить TDD надзвичайно складним, оскільки для кожного тесту доводиться писати великі моки (Mocks) глобального об'єкта `chrome`.

### Стратегія переведення на чистий TDD (Порти та Адаптери)

Щоб покрити написаний код тестами і писати нові фічі тільки через TDD, ми маємо впровадити **Dependency Injection (DI)** (ін'єкцію залежностей) або абстракції.

**Крок 1: Створення Інтерфейсів (Ports)**
Замість прямого виклику `chrome.storage` у класах (як у `ContextManager`), ми створюємо інтерфейс:
```typescript
export interface IStorageAdapter {
  get(key: string): Promise<any>;
  set(key: string, value: any): Promise<void>;
  remove(key: string): Promise<void>;
}
```

**Крок 2: Відокремлення бізнес-логіки (Domain)**
`ContextManager` тепер приймає цей інтерфейс у конструктор:
```typescript
export class ContextManager {
  constructor(private storage: IStorageAdapter) {}
  
  async setTaintedContext(...) {
    await this.storage.set('context', data);
  }
}
```

**Крок 3: TDD Тестування (без браузера)**
У юніт-тестах ми передаємо `InMemoryStorageAdapter`, який імітує пам'ять. Це дозволяє миттєво тестувати будь-яку логіку без `vi.mock('chrome')`.

**Крок 4: Реалізація адаптерів (Adapters)**
У файлах точок входу (`entrypoints/background.ts`) ми створюємо реальний `ChromeStorageAdapter` (який під капотом використовує `chrome.storage.session`) і передаємо його в `ContextManager`.

### План дій:
1. Винести всю логіку з `chrome.*` у папку `src/core/adapters/`.
2. Написати `InMemory` адаптери для локального сховища та повідомлень.
3. Написати юніт-тести для існуючих `ContextManager`, `IntentClassifier` та `VaultScanner`, використовуючи фіктивні адаптери (покриття існуючого коду).
4. Усі нові функції (наприклад, Tab Lineage) розробляти *спочатку* як тести, перевіряючи поведінку на `InMemory` структурах, і лише потім підключати в `entrypoints`.
