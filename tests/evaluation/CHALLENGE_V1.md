# Нові діалоги: challenge-v1

## Навіщо другий корпус

Старі 326 сценаріїв використовувалися для виправлення правил, включно з історичним holdout. Їхній ідеальний результат означає регресійну відповідність відомим очікуванням. Це не незалежний експеримент і не оцінка ймовірності захисту користувача.

Новий корпус перевіряє поточні правила на інших багатореплікових ситуаціях. Його створено та розмічено ШІ, який уже знав проєкт: він **не є сліпим незалежним тестом**. Мітки й SHA зафіксовані до першого запуску в [manifest](challenge-v1.manifest.json). Правила, модель і пороги після отримання результатів не змінювалися. Поточна підготовка навчальних даних читає лише development/regressions.

## Склад

| Розмітка | Діалоги | Інтерпретація |
| --- | ---: | --- |
| threat | 120 | Є конкретний небезпечний запит після встановлення довіри; відомий клас і очікувана дія |
| safe | 80 | Контрастний фінал із збереженням контролю й офіційних процедур |
| ambiguous | 100 | Намір, джерело чи майбутній запит не визначені; потрібні уточнення |

Усього **300 діалогів по 9 реплік**, 2700 повідомлень. 20 сімейств по 15 контрастних фіналів: редакція, новий керівник, старий знайомий, волонтер, романтичне знайомство, ігрова команда, криптоментор, покупець із доставкою, стипендія, медична допомога, рекрутер, сусід, відновлення акаунта, дослідник, контакт підрозділу, інвестиційний клуб, оренда, благодійний приз, юридична допомога та ремонт пристрою.

Спочатку співрозмовник демонструє увагу, спільний досвід або бажання допомогти. Користувач ставить уточнення. Співрозмовник поступово пропонує взяти процес на себе; остання репліка розрізняє атаку, безпечну допомогу та невизначеність. Це контрастний дизайн із повторюваними початками, **не 300 незалежних реальних розмов**. Не діліть сімейство між train і evaluation. Поки в наборі лише українська мова; багатомовність потребує іншої версії.

Тексти вручну прописано у [джерелі генерації](../../scripts/evaluation/create-challenge-v1.mjs), без випадкового добору чи перестановки імен заради кількості. Фінальний [JSON](corpus/challenge-v1.json) є джерелом для runner. Команда генерації не входить до CI та не має API-викликів. Домени `.example` вигадані; реальні приватні листування й ключі не використовуються.

## Що вимірюється

Runner послідовно передає усі репліки до реального `ChatSessionState`, розділяє inbound/outbound, скидає сесію між діалогами та оцінює **кінцевий стан локальних правил** і `getThreatMitigationAction`.

- Precision/Recall/F1: лише 120 threat + 80 safe; правильний тип цими метриками не гарантується.
- Точний збіг: визначені 200 випадків, одночасно правильні detected, intentType та action.
- Хибні блокування: на визначених випадках, де очікували ALLOW/WARN, але отримали LOCK_INPUT.
- Неоднозначні: окремі кількості detected і LOCK_INPUT; вони не зараховуються до TN/FP і не отримують точності «SAFE».
- `expected.action: ALLOW` у ambiguous означає відсутність обґрунтування для примусової дії, а не безпечність співрозмовника.

Синтетичні threat-мітки — гіпотези для аудиту, особливо перенесення розмови до месенджера: такий перехід сам по собі не доводить шахрайство. У нових атакувальних фіналах його поєднано з приховуванням від контролю платформи. Поточний адаптер не перевіряє фактичний показ банера, арбітраж SAFE, маршрутизацію невизначеності до Groq, часові інтервали між репліками або час першого виявлення. Репліки виконуються послідовно без моделювання днів встановлення довіри. Це не браузерне E2E-тестування й не оцінювання shadow-моделі.

## CI та публікація

```sh
# У PowerShell перед запуском: $env:SOVA_EVAL_REPORT = 'metrics/evaluation.json'
npm test -- --exclude 'tests/integration/**'
node scripts/evaluation/generate-dashboard.mjs --report metrics/evaluation.json --out site
```

Обидва корпуси запускаються одним runner. Старі 326 залишають сувору перевірку; challenge записує кожен прогноз і кожну розбіжність. Невідповідність нової мітки не падає як технічний тест. Винятки, невалідні дані, неповний прогін та регресії старого корпусу залишають CI червоним. **Зелений CI і якість розпізнавання — різні показники**, обидва показано у GitHub Summary.

Schema v2: `groups.regression` і `groups.challenge` мають власні розміри, confusion matrix, точний збіг та SHA. Верхні поля `overall`, `totalCases`, `byIntentType` зберігають лише старий корпус для сумісності зі старою історією. `evaluatedCases` = 626. `cases` містить усі прогнози, `scored` позначає виключення неоднозначності, `mismatches` містить лише визначені випадки. Репліки до результатів не записуються. Хешування нормалізує CRLF/LF.

Push у робочі гілки, pull request і ручний запуск створюють обидві оцінки. Pages та `metrics-history` оновлюються тільки з main; metrics-history виключено з push-тригера для запобігання циклу. Історія зберігає агрегати двох наборів, dashboard показує два графіки, розриви за зміни SHA та всі поточні challenge-прогнози. Старі коміти не отримують вигаданих результатів нового набору. Повний детальний JSON останнього прогону можна завантажити зі сторінки; історичні деталі доступні в CI-артефактах у межах строку зберігання, а не в графіку агрегатів.

## Як рухатися далі

1. Незалежний рецензент перевіряє мітки без перегляду прогнозів, відмічає згоду/розбіжності та мотивує рішення.
2. Після перегляду виходить **нова версія** з журналом змін; первинний baseline не переписується.
3. Для порівняння Groq передавати ті самі діалоги через production-псевдонімізацію й builder, без expected, notes, assessment чи family у промпті. Порівнювати local-only, Groq-only та комбінований pipeline окремо. Виклики opt-in із бюджетом RPM/TPM, жодного live запуску тут не проведено.
4. Якщо правила почнуть налаштовувати за цими помилками, challenge-v1 стане відомим benchmark. Для незалежної якості потрібні ще не бачені, окремо зібрані та розмічені розмови.
5. Не обіцяти ефективність у реальному світі за відсотками цього корпусу та не замінювати перевірку UI відповідністю політики дій.
