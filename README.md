S.O.V.A. — відкритий дослідницький проєкт браузерного розширення для виявлення фішингових форм, шахрайських сценаріїв у чатах і спроб виманити чутливу інформацію. Розширення поєднує локальні правила та аналіз контексту; за бажанням можна підключити зовнішнього ШІ-провайдера для додаткової перевірки.

> **Стан проєкту:** активний прототип і дипломний проєкт. Результати тестового корпусу допомагають вимірювати зміни алгоритму, але не гарантують безпеку кожного сайту чи повідомлення.

## Що вміє розширення

- **Аналізувати підозрілі повідомлення.** Шукає ознаки фішингу, шахрайства з оплатою чи доставкою, виманювання контактів та інших сценаріїв соціальної інженерії. Контекст діалогу важливий: окреме слово саме по собі не повинно бути вироком.
- **Перевіряти вебформи.** Виявляє підозрілі приховані поля та невідповідність між чутливими даними у формі й адресою, куди їх планують надіслати.
- **Попереджати про ризиковану дію.** Залежно від типу й рівня ризику система може показати пояснення, попередити перед відправленням або обмежити введення.
- **Пояснювати спрацювання.** Інтерфейс показує, які ознаки вплинули на оцінку, щоб користувач міг зрозуміти причину попередження.
- **Працювати з різними режимами аналізу.** Локальні правила працюють без ключа до хмарної моделі. Додаткових провайдерів, зокрема Groq, можна налаштувати в розширенні.

Перелік функцій і поведінка можуть змінюватися разом із розробкою. Проєкт не замінює антивірус, захист платформи, перевірку адреси сайту чи здоровий глузд.

## Перевірка якості

Проєкт має unit-тести та версійований корпус із загрозливими, безпечними й неоднозначними сценаріями. CI запускає перевірки для змін у `main` і pull request. Публічна панель показує агреговані метрики та їх історію; корпусні повідомлення до неї не публікуються.

Precision, recall і F1 вимірюють якість класифікації саме на наявних тестових прикладах. Результат може змінитися, коли змінюються правила або сам корпус. Живі запити до Groq є окремою інтеграційною перевіркою і потребують API-ключа.

Щоб краще зрозуміти методику й додати тестові приклади, дивіться [опис корпусу та його формату](tests/evaluation/README.md) і [журнал результатів](tests/evaluation/RESULTS.md).

## Запустити локально

Потрібні Node.js **22.12 або новіший** і npm.

```bash
git clone https://github.com/prylutskyy/S.O.V.A..git
cd S.O.V.A.
npm install
npm run dev
```

WXT підготує розширення для розробки. У Chromium відкрийте `chrome://extensions/`, увімкніть режим розробника та завантажте розпаковане розширення з `.output/chrome-mv3`.

Основні команди перевірки й збірки:

```bash
npm run compile       # перевірка TypeScript
npm test              # автоматизовані тести
npm run test:corpus   # оцінювання корпусу
npm run build         # production-збірка
```

Щоб окремо перевірити інтеграцію з Groq, задайте `GROQ_API_KEY` і `GROQ_INTEGRATION=1`, після чого запустіть `npm run test:groq`. Не додавайте API-ключі до коду, тестових даних чи комітів.

## Як долучитися

Не обов’язково одразу писати код — якісний звіт про помилку або добре продуманий безпечний приклад теж допомагає.

1. **Перевірте відкриті [Issues](https://github.com/prylutskyy/S.O.V.A./issues)** або створіть новий. Опишіть браузер, кроки відтворення, очікувану й фактичну поведінку. Не додавайте реальні приватні листування, персональні дані чи API-ключі.
2. **Для змін алгоритму додайте тест.** Хибне спрацювання або пропуск загрози варто закріпити регресійним сценарієм. Додавайте синтетичні приклади та пояснюйте мітку в `notes`.
3. **Змініть код і запустіть перевірки.** Щонайменше виконайте `npm run compile` та відповідні unit-тести; для змін класифікатора — також `npm run test:corpus`. Не налаштовуйте правила за holdout-прикладами: вони призначені для фінальної оцінки.
4. **Надішліть pull request.** Поясніть проблему, рішення, перевірки та можливі компроміси. Невеликі, сфокусовані зміни легше обговорити й перевірити.

Корисні сторінки: [створити Issue](https://github.com/prylutskyy/S.O.V.A./issues/new/choose) · [корпус тестів](tests/evaluation/README.md) · [посібник розробника](docs/DEVELOPMENT_GUIDE.md) · [технічна специфікація](docs/PROJECT_IMPLEMENTATION_SPECIFICATION.md).

## Конфіденційність і безпечне тестування

- Використовуйте синтетичні дані в тестах і звітах.
- Якщо налаштовано хмарного ШІ-провайдера, дані для перевірки передаються йому; перед формуванням запиту система має санітизувати відомі чутливі значення. Не надсилайте секрети й реальні персональні дані для експериментів.
- Тестуйте сценарії виключно на власних сторінках, локальних демо або середовищах, де маєте дозвіл.

Дякуємо за інтерес до S.O.V.A. — долучайтеся через тестування, обговорення й внески в код.
